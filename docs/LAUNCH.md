# Launch readiness

The spec's launch checklist ("Public launch is blocked until every box below is ticked with evidence"), with one verdict per item:

- **DONE**: built and tested; the evidence column names the test or file, and `make gate` / `make launch` re-run it.
- **PARTIAL**: the part that can be done on this machine is done and evidenced; the rest is named.
- **NOT RUN**: could be run, has not been, and why.
- **BLOCKED**: needs an input only the owner can give; the matching row in `BLOCKED.md` says exactly what.

Nothing here is deployed. No box is ticked on the strength of a mock where the checklist asks for the real thing.

## What launch readiness added (this branch)

- Process entrypoints for ingest (`ingest.main:build`) and the orchestrator (`orchestrator.main:build`); every value from the environment (or, for secrets, a file), secrets of at least 32 bytes or the process does not start.
- Images (`infra/docker/build.sh --all`): ingest, api, accounts, orchestrator (with the Docker CLI), reaper (same package, no CLI), web, the Docker filter, plus the worker and egress proxy from M5. All run as uid 10001, built from lockfile-hashed requirements.
- `infra/compose.yaml`: the full stack on one host (below). `infra/compose.env.example` lists every variable; compose refuses to start with any missing.
- **`services/dockerproxy`: the orchestrator holds no Docker socket.** See "The Docker socket" below.
- Secrets are files: `runlog.envfile.secret_env` reads `NAME` or `NAME_FILE`; compose mounts one file per secret under `/run/secrets` and no secret value is in any container's environment (asserted by the smoke against `docker inspect`).
- `scripts/launch_smoke.py` (`make smoke`; `make launch` builds first): boots the stack, then through the **CLI** logs in, plays one scripted run in a real sandbox container and forks it from its session checkpoint. It checks that the fork ends in the parent's exact emulator state, that only the API and web publish a port, that every container is non-root, read-only and capability-free, the Docker-filter attacks from inside the orchestrator, the secrets and network assertions, the security headers on the live web and API (including 404/401), that the provider key is in no container log and not in the object store, and that no sandbox is left behind. The model's answers are scripted by files mounted only by `infra/compose.smoke.yaml` (never in an image); everything else is the production code path.
- The smoke found a real bug: a fork submitted just after its parent ended hit the orchestrator before it freed the per-user slot, and the API answered 502 `internal`. It is now the same 409 `rate_limited` "active run" answer with `Retry-After: 5`, refunds the quota, and is tested.
- Docker tests can no longer run against a stale worker image: `build.sh` labels it with a hash of the sources it contains and `test_docker` fails when the label differs from the tree.

## Deployment requirements (read before exposing anything)

1. **Gateway rules.** In front of GoTrue, block `POST /auth/v1/signup`, `/auth/v1/otp` and `/auth/v1/recover`: they answer differently for known and unknown addresses (account enumeration). Clients use `/api/v1/auth/signup`, `/auth/magic-link` and `/auth/recover`, which answer identically. Also check `Origin` on state-changing requests at the gateway. `api_private` must never be added to PostgREST's `schemas`. (CAPTCHA on sign-up, reset and magic link needs the keys: B-9; the load test needs staging: B-13.)
2. **uvicorn flags.** The API runs with `--ws-max-size 1024` (the 1 KB cap on a WebSocket message must hold before the server reads the message, not only in the app) and `--no-access-log` (the stream ticket is in the `/ws/` URL and must never reach a log). `compose.yaml` sets both, plus `--no-server-header`.
3. **`MEMORYLAB_WEB_TRUSTED_HOPS=1` is only safe behind exactly one proxy that overwrites or appends the real client address.** Vercel overwrites the header; a self-hosted load balancer must **append** (so the client address is the entry one place from the right). Behind no proxy every visitor shares one address at the API; behind a proxy that passes a client-supplied `X-Forwarded-For` through unchanged the per-address limits can be bypassed; behind two, set it to two. The web server refuses to start in production with it unset. The API's own `MEMORYLAB_TRUSTED_PROXY_HOPS` is 1 for traffic from the web server (and for CLI/WebSocket traffic that reaches the API through its own load balancer).
4. **The Docker socket.** The orchestrator must start one sandbox per run, and a raw socket would make a compromised orchestrator root on the host (`docker run --privileged -v /:/host`). So the socket is mounted into `dockerproxy` only (a small in-repo filter, `services/dockerproxy`), on an internal network that only the orchestrator joins; the orchestrator has `DOCKER_HOST=tcp://dockerproxy:2375` and no socket. The filter allows exactly the calls the orchestrator makes (`docker run -i --rm` = create/attach/start/wait, `kill`, `rm -f`, `container inspect`, `network inspect` of the sandbox network) and is default-deny: a create is accepted only if the image is `memorylab-worker:*` as configured, the name and labels identify one run, the user is non-root, the network is the sandbox network, and root filesystem read-only, `CapDrop=[ALL]`, `no-new-privileges`, memory/pids/tmpfs within bounds; it refuses privileged, any bind or mount, capabilities added, host PID/IPC/UTS/user/network namespaces, devices, a different image or network, an unmasking of `/proc`, an unknown HostConfig field, and every other Docker API call (list, exec, pull, build, volumes, networks, logs, archive...). A call on an existing container is forwarded only if the daemon says it is ours (label and name), judged from the daemon's answer. A create is parsed refusing duplicate and case-variant keys (the daemon's decoder is case-insensitive: a second spelling such as `hostConfig` was a host escape in the first version), is validated against exact-case allowlists at every level, and what is forwarded is a new document we built, never the client's bytes. Tests: policy cases, generated case-variant/duplicate/unknown-key cases for every key at every level, a fake daemon that records the forwarded bytes (smuggling, chunked, hijacked attach), the real daemon and CLI (the orchestrator's exact run command works; each escape, including the reviewer's second-spelling payloads, is refused and nothing is created), and the smoke (the attacks from inside the orchestrator container). **Residual:** the filter container itself holds the socket, so a bug in its small parser is the remaining path to the host: keep it off the public network (it is), keep the policy tests, and move to gVisor/Firecracker run workers or Kubernetes (where there is no socket) when hosting is chosen (B-8). Run the orchestrator and the filter only on the dedicated run-worker host, never next to the database or the web server. Set `MEMORYLAB_SANDBOX_RUNTIME=runsc` and add `--runtime runsc` to the filter once gVisor is installed there (B-3).
5. **Egress.** The proxy's allow-list in `compose.yaml` is the ingest service plus one host per allowlisted provider (`api.anthropic.com`, `api.openai.com`, `openrouter.ai`, `api.groq.com`, `integrate.api.nvidia.com`, all :443); it must match the hosts in `labharness.providers.registry`. Add a provider host only with a code review. Sandboxes sit on an internal network with no route out; the orchestrator refuses to start a run if that network has one.
6. **Secrets.** Per environment, generated (`openssl rand -hex 32`), kept outside the repository, never reused. They are files in a private directory (`MEMORYLAB_SECRETS_DIR`, one file per secret, bind-mounted read-only under `/run/secrets`); no secret is an environment variable of any service, so `docker inspect` and `/proc/<pid>/environ` do not show them. What remains in the environment is non-secret configuration and the **public** publishable key. A secret file is still readable by anyone with root on the host and by the service itself; this host model trusts the host operator. The `memorylab_api` login is the API's only database role (never `postgres`); the service-role login is for ingest, the reaper and accounts only.
7. **Networks.** `backend`, `dockerctl` and `sandbox` are internal (no route out). The web server is on `edge` and `upstream` only: no route to ingest (on `backend`), the orchestrator, accounts, the filter or the egress proxy through the internal networks. **Residual in local use:** `upstream` defaults to the Supabase CLI's own network, which is flat, so ingest, accounts and the API (which sit on it to reach Postgres/GoTrue) are reachable from the web container there; they are token-protected and the smoke asserts the web container cannot reach the orchestrator, the filter or the proxy, but not ingest/accounts. With hosted Supabase, point `UPSTREAM_NETWORK` at a bridge created with `com.docker.network.bridge.enable_icc=false`: containers on it can call out to the hosted project but not each other.
8. **Object store.** The compose volume is the local store (B-2); the API mounts it read-only. Production presigns from S3-compatible storage; until then the API's frame and export URLs are served by the local signer.
9. **Fixture only.** The images ship the CC0 fixture game so the stack can run. A public game is B-7.

## How to reproduce the evidence

```bash
supabase start --workdir infra
make gate          # lint, mypy, every Python suite, web (vitest, build, bundle scan, Playwright), gitleaks
make launch        # build every image, then boot compose and run the smoke
```
